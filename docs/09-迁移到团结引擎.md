## 3. Git 历史是怎么接上的


### ⚠️ 血的教训：不要用 PowerShell 改这个工程的文本文件

第一轮是用 PowerShell 5.1 的 `Set-Content -Encoding UTF8` 批量改的，结果：

- PS 5.1 的 `-Encoding UTF8` **会加 BOM**，而且**按系统 ANSI 代码页读入**原文件；
- 中文注释被读成乱码再写回，`[Header("闪白")]` 变成 `[Header("鍑婚€€涓庣‖鐩?)]` —— **关闭引号被吃掉**，后面 234 行全部 `CS1010 / CS1026 / CS1003 / CS8086 / CS1039`；
- 5 个文件全部报废：`HitReaction.cs`、`EnemyController.cs`、`PlayerController.cs`、`RoomManager.cs`、`Projectile.cs`。

修法：从 `D:\Roguelike2D` **逐字节拷回**这 5 个文件的 `.cs` + `.meta`，然后改用带编码保护的编辑工具重做 22 处改动。

**结论：这个工程里所有文本文件（`.cs` / `.asset` / `.prefab` / `.unity` / `.md` / `.ps1`）一律用 UTF-8 无 BOM 写。** 唯一的例外是 `Tools/setup-git.ps1`（PS 5.1 需要 BOM 才不会把中文读成 GBK）。

## 5. 冲突二：包依赖降级

### 原 `Packages/manifest.json`（Unity 6000.3）

```
com.unity.feature.2d 2.0.2 / com.unity.ide.rider 3.0.40 / com.unity.ide.visualstudio 2.0.26
com.unity.inputsystem 1.20.0 / com.unity.test-framework 1.6.0 / com.unity.timeline 1.8.12
com.unity.ugui 2.0.0 / com.unity.visualscripting 1.9.12
```

### 现 `Packages/manifest.json`（团结 2022.3）

```
com.unity.ide.rider 3.0.24 / com.unity.ide.visualstudio 2.0.18
com.unity.inputsystem 1.7.0 / com.unity.ugui 1.0.0
+ 31 个 com.unity.modules.* 1.0.0
```

解析结果：`packages-lock.json` 共 **38 个包**（depth 0 的是上面 4 个 registry/builtin + 31 个 modules；传递依赖只有 `com.unity.ext.nunit 1.0.6`、`com.unity.test-framework 1.1.33`、`com.unity.modules.subsystems`）。

### 为什么砍掉 `com.unity.feature.2d`

团结的 `BuiltInPackages` 里 `com.unity.feature.2d` 是 **2.0.1**，它会拉 8 个子包（2d.animation / pixel-perfect / psdimporter / sprite / spriteshape / tilemap / tilemap.extras / aseprite）+ `com.unity.burst` + `com.unity.collections` + `com.unity.mathematics`。

但扫描 `Game.unity` + 4 个预制体后：`Tilemap` / `SpriteShape` / `PixelPerfectCamera` / `Aseprite` / `PackedSprite` / `Animator` / `Light2D` **全部 0 命中**，只有 `SpriteRenderer` ×18、`Rigidbody2D` ×6、`BoxCollider2D` ×12、`CircleCollider2D` ×2、`CapsuleCollider2D` ×4 —— **全是引擎内置组件**。而且工程里一张图片都没有。

→ 判定 `feature.2d` 纯属白拉，直接从 manifest 移除，`Library/PackageCache` 里对应目录一并清掉重解析。
`com.unity.ugui` 在团结里是 **内置包（1.0.0）**，写 `2.0.0` 会解析失败，必须降到 `1.0.0`。

### 包装类的自动重生成（不用管）

`Assets/_Project/Settings/PlayerInputActions.cs` 是 Input System 的代码生成器产出的。打开工程后团结用 1.7.0 的生成器**自动重写了它**：31,679 B / 692 行 → **19,186 B / 476 行**，文件头的 `version 1.20.0` 变成 `version 1.7.0`。这是预期行为，**不要手动改这个文件**（它由 `PlayerInputActions.inputactions` 生成）。

## 6. 冲突三：内置资源引用全部失效（「运行后看不到东西」的根因）

Unity 的内置资源包（`unity_builtin_extra` 等）在团结里被**重新打包并改名**成了 `tuanjie_builtin_extra`，于是 Unity 那套内置 GUID 在团结里全部指向不存在的资产。

实测证据：

```
AssetDatabase.GUIDToAssetPath("311925a002f4447b3a28927169b83ea6") = ''        ← Unity 的内置方块，团结里不存在
AssetDatabase.GUIDToAssetPath("0000000000000000f000000000000000") = 'Resources/tuanjie_builtin_extra'
Resources.InstanceIDToObject(7482667652216324306) = null                      ← 原内置方块
```

影响面：`Game.unity` 1 处 + `Room_01.prefab` 7 处 + `Room_02.prefab` 8 处 + `Fireball.prefab` 1 处 + `MageBolt.prefab` 1 处 = **18 个 SpriteRenderer 的 sprite 全变 null**。运行时只剩相机背景色和 HUD 血条 —— 和「运行后看不到东西」的现象完全对得上。

> 这个工程**原本就没有任何美术资源**（`Art/` 下只有 `.gitkeep`），所有可见物体都是靠 **Unity 内置白方块 / 白圆 + `SpriteRenderer.m_Color` 染色**。所以内置资源一失效，画面就整个空了。

### 修法一：按原始 fileID 还原形状，而不是统一填一张占位图

失配后 sprite 在对象层就是 `null`，看不出「原本是方块还是圆」。唯一可靠的线索是 `SerializedProperty.objectReferenceInstanceIDValue` —— 它保存着**原来的内置 fileID**：

| 原内置精灵 | GUID | fileID | 迁移前用在哪 |
| --- | --- | --- | --- |
| `Square`（方块） | `311925a002f4447b3a28927169b83ea6` | `7482667652216324306` | Player、地板、门、敌人、尖刺（16 处） |
| `Knob`（圆） | `a86470a33a6bf42c4b3595704624658b` | `-2413806693520163455` | Fireball、MageBolt 两个投射物（2 处） |

第一轮图省事，18 处**全填了方块**，结果法师的投射物从圆形变成了方形（用户反馈）。第二轮改成按 fileID 查表分派，才正确。

新增两个占位精灵（程序生成，`TextureImporter` 设 `spritePixelsPerUnit = 32`，32×32 → 正好 1 个世界单位，与原内置图形尺寸一致；`FilterMode.Point`、关 mipmap）：

| 占位图 | 字节 | GUID |
| --- | --- | --- |
| `Assets/_Project/Art/Placeholder/Square.png` | 107 | `1622f347918d6d344918a4aa53fdbacc` |
| `Assets/_Project/Art/Placeholder/Circle.png` | 433 | `7d50da08d6c27ad4698f347ac2d3181a` |

**教训：迁移内置资源引用时，不能「看到引用坏了就统一填一张占位图」，必须先按原始 fileID / 类型还原形状。**

### 修法二：房间锚点在相机视野外（源工程自带的摆放问题）

`RoomManager` 在场景里的 Transform 原本是 **x = 15.30789**，而相机（正交 size 5、aspect 1.333）可视范围只有 **X[-6.70, 6.64] Y[-5.03, 4.97]**。`RoomManager.roomAnchor` 是空引用，`AnchorPosition` 退化成 `transform.position` → 房间被生成在视野之外。

已把 `RoomManager` 的 Transform 改成 `{x: 0, y: 0, z: 0}`（房间预制体是围绕局部原点搭的，出生点局部坐标就是 `(0,0,0)`，所以原点即房间起点）。

改完后编辑模式预览：房间 7 个可见物体里 **1 个落在相机视野内**（`Ground` 地板，20 单位宽），玩家出生点在 `(0,0,0)` 也在视野内；其余 6 个（`Ground(1)` x=20、`Ground(2)` x=40、`Dummy` x=12、`Spike` x=10、`Enemy` x=7.58、`Door` x=14）需要向右走才进视野 —— 这是**原关卡长度，没有改**。

### 顺带：脚本 `.meta` 的 GUID 形态

团结把部分脚本的 `.meta` GUID 从 32 位 hex 改成了 **56 字符 base64 形态**（例如 `RoomManager.cs.meta` 是 `W3gbvH6rAnIAZCCku7IZN+BGpamosp0LZ4tp3+UPX75OUILN/dWKa8E=`），而场景里对这个脚本的引用仍是旧的 32 位 hex。**两种形态都能正确解析到同一个脚本，不是失配**。非脚本资产（`.inputactions` / `.asset` / `.unity` / `.prefab`）的 GUID 与源工程保持一致。

### 自检脚本里踩过的几个坑（留作经验）

- **`MonoScript.GetClass() != null` 不是「脚本编译成功」的判据**，只是「有组件类」。`PlayerInputActions` 是普通类（`IInputActionCollection2`），必然返回 null。现在的判定改成：**先收集被场景/预制体 `m_Script` 引用的脚本**，只有「被引用却 `GetClass() == null`」才算 FAIL。
- **未打开的预制体不在 `FindObjectsOfType` 的搜索范围内**，扫预制体必须 `PrefabUtility.LoadPrefabContents` 之后再扫（第一版把扫描放在加载之前，4 个预制体全漏了）。
- **`Application.isBatchMode` 下 `EditorApplication.EnterPlaymode()` 不可用** —— 实测挂在 `Loaded scene 'Temp/__Backscenes/0.backup'`，10 分钟没动。所以运行时验证改用**编辑模式预览**（`团结/可见性预览` 菜单，按运行时逻辑把房间摆到锚点上再算可见性）。
- **批处理退出码 0 ≠ 没有编译错误**：一度出现 `error CS0103: The name 'StringComparison' does not exist`，但报告文件还是上一轮的旧内容。判断一轮跑没跑成功，要看**报告文件的 LastWriteTime / 字节数有没有变**。

## 11. 复现这条迁移路径的最短步骤

1. 装团结编辑器：`D:\Tuanjie\Editor\2022.3.62t16\`（Hub 里 `tuanjie install 1.10.4`）。
2. 拷源码：`Assets/` + `Packages/` + `ProjectSettings/` + `docs/` + `Tools/` 从 Unity 工程复制（**不要**拷 `Library/`）。
3. 改 `Packages/manifest.json`：删 `com.unity.feature.2d`，`ugui` 降 `1.0.0`，`inputsystem` 用 **1.7.0**，`rider` 用 **3.0.24**，`visualstudio` 用 **2.0.18**，删 `test-framework`/`timeline`/`visualscripting`。
4. 清 `Packages/packages-lock.json` 与 `Library/PackageCache`，让团结重新解析（38 个包）。
5. 全局替换 Unity 6 的 API（`linearVelocity` → `velocity`，`FindFirstObjectByType` → `FindObjectOfType`，`FindObjectsByType` → `FindObjectsOfType`），**用 UTF-8 无 BOM 写**。
6. 按原始 `objectReferenceInstanceIDValue` 把失效的内置精灵引用重映射到自建占位精灵。
7. 跑自检（第 7 节），确认 `error CS` = 0、Missing Script = 0、失效引用 = 0。
