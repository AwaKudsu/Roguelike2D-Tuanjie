## Day 1 · 工程搭建与水平移动

### 1. `.gitignore` 不支持行尾注释，规则会静默失效

**现象**：配置了 `.gitignore` 忽略 `Library/`，但自检时发现它**根本没被忽略**，`git check-ignore` 报告未命中。

**根因**：写成了这样——

```gitignore
/[Ll]ibrary/          # 资源导入缓存
```

Git 会把**整行**当成要匹配的字面量（包含 `#` 和后面的中文），永远匹配不到任何文件。**`#` 只有在行首才是注释**（`.gitattributes` 同理）。

**解法**：说明单独占一行。用 `git check-ignore --no-index -v "<路径>"` 逐条验证，不靠肉眼看。

**为什么危险**：`git status` 在 `Library/` 还没生成时看起来一切正常，等你发现时可能已经提交了几百 MB 进去。

### 2. PowerShell 5.1 读取无 BOM 的 `.ps1` 会按 GBK 解码

**现象**：脚本报出一堆毫不相关的语法错误——

```
The '<' operator is reserved for future use.
The string is missing the terminator: '.
Unexpected token '鏈厤缃?' in expression or statement.
```

**根因**：`.ps1` 存成了 UTF-8 **无 BOM**，而 Windows PowerShell 5.1 在中文系统上会按 **ANSI(GBK)** 解码。中文变成乱码字节后，把字符串的引号配对也一起破坏了，于是错误定位完全指向不了真正的原因。

**解法**：把 `.ps1` 存成 **UTF-8 with BOM**，或改用 PowerShell 7（`pwsh`）运行。

```powershell
[System.IO.File]::WriteAllText($p, $text, (New-Object System.Text.UTF8Encoding($true)))  # $true = 带 BOM
```

### 3. Unity 6 把 `Rigidbody2D.velocity` 改名为 `linearVelocity`

**现象**：照抄网上教程写 `_rb.velocity`，出现弃用警告。

**根因**：Unity 6 为了和 3D 的 `Rigidbody.linearVelocity` 统一命名，重命名了 2D 版本。**网上绝大多数教程还是旧写法。**

**解法**：项目锁定 Unity `6000.3.22f1`，统一使用 `_rb.linearVelocity`。

### 4. Sprite 看得见 ≠ 撞得到（缺 Collider2D）

**现象**：角色下落时**直接穿过地面**。Console 没有任何报错。

**根因**：三块地面对象上只有 `SpriteRenderer`，**没有 `Collider2D`**。

| 组件 | 作用 | 没有它会怎样 |
| --- | --- | --- |
| `SpriteRenderer` | 看得见 | 屏幕上是透明的 |
| `Collider2D` | 撞得到 | 直接穿过去 |

两者**完全独立**。当时的状态是「画出来了但物理上不存在」。

**解法**：给每块地面加 `BoxCollider2D`。缩放 `(20,1,1)` 会自动把碰撞体放大成 20×1。

**沉淀出的排查清单**（Console 没红字 = 不是代码问题，先查配置）：

1. 双方都有 `Collider2D` 吗
2. `Is Trigger` 勾了吗（勾了只触发事件，不阻挡）
3. 至少一方有 `Rigidbody2D` 吗（两个纯静态碰撞体之间不碰撞）
4. `Layer Collision Matrix` 里这两层允许碰撞吗
5. 缩放是 0 吗（会让碰撞体退化消失）

### 5. Play 模式下改 Inspector 数值，停止运行会全部还原

**现象**：运行中把 `deceleration` 从 80 调到 25，手感满意；停止运行后数值弹回 80。

**根因**：Unity 的默认行为——**Play 模式下的序列化字段修改不会保存**。

**解法**：调参流程固定为「运行中试 → 记下满意值 → 停止 → 在编辑模式重新填 → `Ctrl+S`」。

**为什么要专门记**：不知道这条的人会反复「调好手感 → 一停止全没了」，还以为是记错了。

### 6. `.meta` 文件必须提交

**现象**：Unity 首次打开工程生成了 37 个 `.meta` 文件，全部处于未跟踪状态。

**根因**：`.meta` 记录每个资源的 **GUID**，工程内所有引用都靠 GUID 定位。漏提交的后果是**别人克隆后引用全部断裂**（满屏 `Missing Reference`）。本地看不出问题，因为文件就在磁盘上。

**解法**：`.gitignore` 里必须保留 `!/[Aa]ssets/**/*.meta` 这条例外规则，每次新增资源都确保 `.meta` 一起提交。

## Day 2 · 跳跃手感四件套

### 实现内容

| 机制 | 作用 |
| --- | --- |
| 土狼时间 Coyote Time `0.1s` | 离开平台后仍可起跳的宽限 |
| 跳跃缓冲 Jump Buffer `0.1s` | 落地前提前按跳，落地瞬间自动起跳 |
| 可变跳跃高度 `jumpCutMultiplier 0.45` | 按得久跳得高，用同一个键覆盖 20%~100% 高度区间 |
| 双重力 `rise 3.5 / fall 6` | 下落比上升快，落地更干脆 |

### 7. Update 与 FixedUpdate 频率不同步会导致输入事件丢失

**现象**：偶发「按了跳跃但没反应」，概率很低但确实存在。

**根因**：`Update()` 跟随渲染帧率（可能 144 次/秒），`FixedUpdate()` 固定每秒 50 次。**一次极短的按键可能整个落在两次 FixedUpdate 之间，被完全错过。**

**解法**：输入层用**锁存 + 消费**模式——事件发生时先存下来，由逻辑层主动「取走」：

```csharp
private bool _jumpPressedLatch;

public bool ConsumeJumpPressed()
{
    if (!_jumpPressedLatch) return false;
    _jumpPressedLatch = false;   // 取过一次就没了
    return true;
}
```

**为什么不能用普通的 bool 标记**：FixedUpdate 连续跑两次就会消费同一个按键两次，可能触发两次跳跃。`Consume` 语义上等于**从信箱里把信拿走**。

---

### 8. 跳跃缓冲 + 过大的地面检测半径 = 「没落地就起跳」⭐

**现象**：从空中落地时按跳，角色**看起来还没碰到地面就弹起来了**。

**根因（数值层面）**：地面检测用的是以脚底为圆心、半径 `0.15` 的 `OverlapCircle`。

```
角色高 1 单位，半径 0.15
→ 只要地面距离脚底 ≤ 0.15 单位就判定为「已落地」
→ 也就是提前 15% 身高变 true

放到屏幕上：角色高 200px 时，脚底离地还有 30px 就已经算落地了
```

再加上跳跃缓冲会在 `IsGrounded` 变 true 的**当帧立刻起跳**，于是角色在还差 30px 时才「被判定落地」，视觉上就是空中起跳。

**根因（设计层面）**：把两种容错混在了一起。

> **地面检测应该回答「我踩到东西了吗」，而不是「我离地面近吗」。**
>
> 「离得近也算」是留给玩家的容错——但容错应该由**跳跃缓冲**和**土狼时间**提供，不该由地面检测提供。

**解法**：`groundCheckRadius` 从 `0.15` 收紧到 `0.05`。0.05 远大于 Unity 2D 物理的接触偏移（`0.01`），不会漏判；又小到肉眼看不出提前量。

**沉淀出的经验**：Scene 视图里的 Gizmos 检测圆是判断地面检测是否准确的直观工具——**贴着脚底才是对的**，拖出脚底一大截就是提前量。

---

### 3 个手感机制的分工（Day 2 的核心认知）

| 机制 | 性质 | 目的 |
| --- | --- | --- |
| 土狼时间 | **容错** | 不惩罚「踏空瞬间才按跳」 |
| 跳跃缓冲 | **容错** | 不惩罚「落地前提前按」 |
| 可变跳跃高度 | **表达** | 让玩家能做更多的事（短跳躲避 / 长跳跨越） |

前两个是让玩家**不易失误**，第三个是让玩家**有表达力**。性质不同，调参思路也不同：容错机制调到「能感觉到但不明显」最舒服，表达机制则要差别足够大才有意义。

## Day 6 · 房间与 HUD

### 9. 在 `Awake` 里读「别的组件在 `Awake` 里写的值」⭐

**现象**：房间里的敌人一个都没死，玩家走过去碰一下门，就被传回出生点（门一开局就是开的）。也就是说「清光敌人才开门」这条规则完全没生效。

**排查顺序**：先查配置，配置全对才怀疑代码。
- `Room_01.prefab` 里 `Room` 组件的 `requireClear: 1` ✅
- `spawnPoint` 和 `door` 两个引用都指向了正确的对象 ✅
- `Enemy` 确实是根物体 `Room_01` 的子物体（在 `m_Children` 列表里）✅

配置没问题 → 问题在代码。

**根因**：

```csharp
// Health.cs
private void Awake()
{
    _stats = GetComponent<CharacterStats>();
    Current = maxHealth;        // ← Current 要到这里才有值
}

// Room.cs（错的写法）
private void Awake()
{
    // ...收集敌人列表...
    RecountAlive();             // ← 读 Health.IsAlive（= Current > 0f），此刻 Current 还是 0
}
```

`Room` 挂在房间**根物体** `Room_01` 上，`Enemy` 是它的**子物体**。Unity 实例化预制体时，**根物体的 `Awake` 先于子物体执行**。于是：

1. `Room.Awake()` → `RecountAlive()` 读到每个敌人的 `Current` 都是 `0` → `IsAlive` 全是 `false` → `AliveEnemies = 0`
2. `Room.Start()` → `EvaluateClear()` → `requireClear && AliveEnemies > 0` 为假 → 判定「已清场」→ `door.Unlock()`
3. 门从实心墙变成触发器 → 玩家走进去 → `RequestAdvance()` → `IsCleared` 已经是 `true` → `Advance()` → 传回出生点

**解法**：把 `RecountAlive()` 从 `Awake()` 挪到 `Start()`。

**为什么这样就好了**：Unity 有且只有一条关于初始化顺序的强保证 —— **「所有物体的 `Awake` 都跑完，才会跑第一个 `Start`」**。把读取放进 `Start`，就一定晚于所有 `Awake`。

**判断标准**（以后照着问一句就行）：

> 我读的这个值，是**别的组件在它自己的 `Awake` 里写的**吗？
> 是 → 必须放 `Start`。不是（读的是自己的字段、Inspector 序列化值、或者 `GetComponent` 拿到的引用）→ 放 `Awake` 没问题。

**同一个规律，本项目已经踩到第二次**：Day 4 的 `CharacterStats.SyncMaxHealthToHealth()` 也是因为这个才必须放 `Start` —— `Health.SetMaxHealth()` 内部要按 `Current / maxHealth` 算比例，而那一刻 `Health.Current` 还是 `0`，比例算成 0，换职业就会以 0 血开局。两次的现象完全不同（一次是门乱开，一次是没血），根因是同一条。

**附带加的一行日志**：`Room.Start()` 末尾打印 `[Room] xxx：敌人 N 个，门已开/锁着`。这类「门为什么开了」的问题看画面很难判断，看一行数字一眼就清楚。

## Day 21 · 大厅灯光与「人物下不来」

### 10. 俯视房间里放一块整间房大小的实体地板，角色会被从内部挤出去

**现象**：在大厅点「确认」后，角色确实出现在选中的台子上，但整个人被顶到大厅顶部、贴着上墙和挂毯，往下走一步就被弹回去，只剩左右能动。

**根因**：`LobbyRoom/Shell/Floor` 上挂着一个 `BoxCollider2D`，尺寸 `23 × 15`（比房间 20 × 10 还大一圈 —— 当初是为了让平铺贴图在任何窗口比例下铺满整屏，顺手把碰撞体也设成了同样的尺寸，`isTrigger = false`）。

俯视大厅里没有重力，玩家是 `Dynamic` 刚体、靠 `velocity` 驱动。`ConfirmPick()` 把玩家传送到台子脚下 `(13.4, 6.2)`，这个点在**地板碰撞盒内部**，Box2D 会沿**穿透最浅的方向**把人推出去：

| 到盒子的面 | 距离 |
| --- | --- |
| 上表面 y = 12.5 | 6.3 |
| 右表面 x = 21.5 | 8.1 |
| 下表面 y = −2.5 | 8.7 |
| 左表面 x = −1.5 | 14.9 |

最近的是上表面，于是每帧都往上顶；而上墙的碰撞盒在 `y 9…10`，人就被夹在「地板往外推」和「上墙往里挡」之间，稳定停在 `y ≈ 8.2` —— 正好是截图里法师悬在旗帜旁边的位置。玩家只在确认后才显示，所以看上去像「一确认就卡上去了」。

**解法**：删掉 `Floor` 的 `BoxCollider2D`，房间边界只由**四面墙**负责（墙的碰撞盒本来就贴着房间内边界）。同时：

- `LobbyRoomBuilder` 不再对地板调用 `AddCollider`（重跑生成菜单也不会把坑加回来）
- `LobbyRoomCheck` 的断言反过来：**地板必须没有碰撞体**，有碰撞体反而报 FAIL

**教训**：横板游戏的地板要「实体」，俯视游戏的地板只要「图」。同一个 `Collider2D` 在两种视角下的语义完全不同 —— 换个视角时先问一句「这块碰撞体在挡谁」，别把上一套视角的经验直接搬过来。

### 11. 光晕是「缩放的贴图」，大小写在两处

**现象**：大厅墙根的暖光糊了大半间房，画面又亮又脏，火把和石柱都糊在光里。

**根因**：`LobbyGlow.png` 是 96×96、PPU 96 的**1 单位**软光斑，`NewGlow(parent, name, pos, size, color, order)` 内部只是把 `localScale` 设成 `(size, size, 1)`。生成时给的 `size = 8`，于是每一团光都是 **8 × 8 单位**，而房间才 20 × 10；再叠上 `alpha 0.45`，等于半间房盖了一层橙色。

**解法**：`Light_Left/Right` 收到 **5**、`alpha 0.3`；`Light_Door` 也收到 5、`alpha 0.18`（门光本来就该更冷更淡）。

**同一个坑的老问题**：这些数值在 **`LobbyRoomBuilder` 和 `Game.unity` 里各存一份**。只改场景、不改生成器，下次点「团结 → 生成元气骑士式大厅」就被写回旧值；只改生成器、不改场景，这次运行看到的还是旧值。**两边一起改**才不会再踩。

## Day 22 · 大厅镜头：放大一档 + 跟着人走

### 12. 房间正好一屏时，「跟随镜头」无处可去

**现象**：大厅视野原本 `lobbyCameraSize = 5`，房间 20 × 10、画面 17.8 × 10 —— **房间高就等于画面高**，整间房刚刚好卡满屏幕。选人的确认框又从下方盖掉 40%，实际能看到的只剩上半间房，观感上就是「视角太小」。想让镜头跟着人走，却发现人走两步镜头就得动，一动就露出地板外面。

**根因**：正交相机 `orthographicSize` 是**半个画面高**。画面 ≥ 房间，镜头就没有可移动的余量；要么把画面缩小（视野反而更小），要么把房间/地板做大。想要「跟」，就得先有「能跟的空间」。

**解法**：

1. `lobbyCameraSize` 5 → **6**（16:9 下画面 21.3 × 12，整间房 + 外圈地板都在画面里）
2. 地板多铺一圈：`FloorMarginX/Y` 1.5 / 2.5 → **5 / 3.5**，地板 23 × 15 → **30 × 17**；`LobbyRoom` 新增 `floorPadding` 存同一组数
3. `LobbyRoom.FollowPlayer(dt)`：确认之后（`Stage.Walking`）每帧向人物位置靠，用 `1 - e^(-k·dt)` 做指数插值（掉帧不变手感）
4. `LobbyRoom.ClampCameraToFloor`：先把目标点夹进「房间 + 地板外圈 − 半个画面」的矩形，跟到边上就停住 —— **宁可不动，也不露相机底色**；画面比地板还宽（超宽屏）时直接退回房间正中

**教训**：镜头跟随不是给相机加个 `Lerp` 就完事，得先算清楚「跟随范围 = 世界尺寸 − 画面尺寸」。世界比画面小的时候，跟随的真相就是「什么都不动」。

## Day 23 · 灯光：对准火苗、不穿墙

### 13. 光斑中心是「贴图中心」，不是「火苗」

**现象**：大厅里两团暖光看着像浮在地上的光球 —— 最亮的一圈落在火把杆子上，甚至偏到杆子右下；同时上墙和墙外的岩石都被照亮，房间像在漏光。

**根因**是两件事叠在一起：

1. `Light_Left/Right` 的坐标是 `(3.4, 8)` / `(16.6, 8)`，火把在 `(2.9, 8.1)` / `(17.1, 8.1)` —— x 差 0.5、y 差 0.1；
   而火把贴图中心对齐、火苗又在中心**上方 0.4**。三个偏移叠起来，最亮的中心自然不在火苗上。
2. 4.5 单位的光斑挂在 y ≈ 8，一半越过上墙（y 9…10）。墙砖只在 9…10 那一条，挡不住越过去的部分，
   于是光糊在了墙外的岩石上。

**解法**：

- 位置不再手写第二份坐标：`Light_Left/Right` 直接用 `(TorchLeftX, TorchY + 0.4)`，跟火把共用常量
- 给房间加一块 `SpriteMask`（`Shell/LightMask`，20×10），灯光设 `maskInteraction = VisibleInsideMask`，
  custom range 只盖 `-199…-190` 这一档 —— 光剪在房间内，地板/地毯/石台光圈都不受影响

**教训**：程序化生成的房间里，所有「挂件」的位置都该**由被挂的东西算出来**（火把 x、火苗偏移）。
手写的第二份坐标不会立刻出错，只会慢慢和第一份错开 —— 错开的时候你还以为是自己眼花了。

## Day 24 · 大厅四方向朝向：给正/背视图留插槽

### 14. 侧视帧当不了「正对镜头」

**现象**：大厅里按 S 往下走，人还是侧着身子（甚至被镜像成朝左），像贴图在地面上横着平移；
按 W 往上走更奇怪 —— 看到的是正面。

**根因**：整套角色帧是给横板关卡画的，45 张全是侧视。`LobbyAvatar` 只会做一件事：
`move.x` 一变就 `flipX`。俯视的四方向里，「下」和「上」根本没有对应的图可用，
代码怎么改都只能拿侧视图顶着 —— **这是素材问题，不是逻辑问题**。

**解法**（先留插槽，再补图）：

- `ClassData` 加三个可选 `Sprite`：`lobbyFront`（下）/ `lobbyBack`（上）/ `lobbySide`（左右）
- `LobbyAvatar` 按输入切图，判据是「纵向明显压过横向」才切（`verticalBias = 1.15`），
  斜着走保持侧视 —— 只有四方向图时，斜向用侧身最自然
- 三张都可以空：空了回退到侧视 + `flipX`，和改之前一模一样，不会白块
- 图按 `Art/Characters/<职业>/<职业>_Front|_Back|_Side.png` 命名，菜单
  **团结 → 同步大厅朝向图** 一次性写进所有 `ClassData`
- 战士的 `Warrior_Idle` 本来就是正对镜头的，直接指给 `lobbyFront` —— 战士今天就正确了；
  法师还缺正面/背面，先靠回退

**教训**：「朝向不对」这种反馈，先问一句 **缺的是哪张图**。
在只有侧视帧的工程里加四方向逻辑，能做的只是「把缺图这件事变得可填」，
不能靠代码把侧面变成正面。

**顺带挖出来的**：`WarriorVisual` / `MageVisual` 的 `Update` 每帧都 `Apply(ChooseFrame())`
写 `sprite.sprite`。大厅里 `LobbyAvatar` 挨个换正面/背面图，写完下一帧就被动画盖回去 ——
所以进出大厅时用 `PlayerVisualSwitcher.SetLobbyMode(true/false)` 把整套关卡动画停掉，
`ApplyVisualEnable()` 同时看「是不是大厅」和「是不是法师」两个条件。
「两个组件写同一个渲染器」这种抢帧，症状往往不是报错，而是你怎么改都没反应。

## Day 25 · 背包界面重做：左边人物与属性，右边分类物品

### 15. `FindObjectOfType<Health>()` 会拿到敌人的血

**现象**：背包左侧的「生命」一栏显示 `37 / 140`，可人物明明满血 —— 37 是场上某个小怪的血量。

**根因**：`Health` 是通用组件，敌人身上也挂。`FindObjectOfType<Health>()` 返回哪个完全取决于
加载顺序，跟「是不是玩家」没有半点关系。

**解法**：从已经确认是玩家身上的组件往上要 —— `inventory.GetComponent<Health>()`。
`Inventory` 只在玩家身上有，它所在的那个物体就是判据。

**教训**：`FindObjectOfType` 只在你确认真个场景里只有一份时才安全。
「玩家的血」这种问题，正确答案永远是「从玩家身上拿」，不是「找第一个 Health」。

### 16. 格子只有 96 像素，图标和名字抢地方

**现象**：第一版把 64 像素图标放在格子中间、名字压在最底下，图标直接把名字盖住了。

**根因**：`CellSize = 96`，图标 64 居中就是 y −32…+32，名字占 y 4…30，两者重叠 28 像素。

**解法**：装备没有图标（`ItemData.icon` 留空时 UI 画一个稀有度色块），名字本来就承担了
「这是什么」的全部信息，所以名字优先 —— 图标缩到 40、抬到 y +20（占 0…40），
名字占 −44…−4，中间不留缝也不重叠。装备槽只有六个、名字靠槽位本身就能认，图标给 44。

**教训**：格子类 UI 先定「文字占多少」，再拿剩下的空间放图。
反过来的话，图永远比你以为的更能挤。

### 17. 代码搭 UI 时，两个矩形「各算各的」就一定会撞

**现象**：第一版跑起来一眼看到三处叠：属性卡最后一行「冷却缩减 0%」被底部提示条的
「Tab 关闭」压在同一个像素行上；职业名「法师」落在角色卡的下边框外面；三个装备槽
比卡片底色还暗，看上去是一整条深色长条。

**根因**：三处都是**两份坐标各自独立算出来**，没有一个地方保证它们不重叠 ——
提示条按「窗口宽度 − 80」铺满整行，自然会横穿左侧的卡片；职业名按「卡片半高 + 30」
贴边，而立绘也按同一套中心坐标排，谁也没让谁；格子底色 0.11 比卡片 0.13 暗，
画上去等于没画。

**解法**：给每一块先写清「上沿 / 下沿」再反推中心与高度，把数字写在常量注释里：

```csharp
private const float CharCardY = 130f;   // 上沿 270、下沿 -10
private const float StatCardY = -186f;  // 上沿 -36、下沿 -336
```

提示条改成只占右侧（`x = 195`、宽 740），装备槽底色提到 0.17 并留 4 像素缝，
职业名压到卡片下沿 28 像素以内。

**教训**：运行时搭界面没有 Rect Tool 帮你挡，重叠只能靠**数字对得上**。
每个块在常量旁边写一句「上沿/下沿是多少」，比事后截图找叠字快得多。

## Day 26 · HUD 重排：立绘 + 血条 + 蓝条 + 技能栏

**要解决的问题**：血条蓝条的「表现不太好」——只有两条光秃秃的色块在左上角飘着，
掉了多少血看不出来；技能栏又孤零零待在左下角，眼睛要在屏幕两个角之间来回跳。

**做了什么**：

1. **布局**：新建 `PlayerHud` 容器（`600 × 174`，锚左上 `24, -20`），把四样东西塞进去：

   | 部位 | 位置（相对容器） | 尺寸 |
   |---|---|---|
   | 底板 `PanelBorder` / `PanelFill` | `0, 0` / 内缩 2 | `600 × 174` |
   | 立绘 | `12, -12` | `110 × 110` |
   | 血条 | `134, -14` | `440 × 32` |
   | 蓝条 | `134, -54` | `440 × 24` |
   | 技能栏 | `218, -88` | `4×62`，间距 8 |

   立绘在左、条在右、技能在条下面 —— 这就是 DNF 那种一眼能扫完的排法。
   以后整块挪位置，只改 `PlayerHud` 一个坐标。

   第一版没有底板，四样东西各飘各的（截图里就是「太分散」），而且血条 430、蓝条 340
   左右不等宽，视觉上根本不成一块。第二版加了 `PanelBorder`（2px 描边）+ `PanelFill`
   （深色底），条改成同宽 440，技能栏在条下面**居中**，才连成一块。

2. **`StatBar` 加残影（ghost）**：挨打时 `fill` 立刻缩短（`catchUpSpeed 4`），
   底下那层浅色残影用 `ghostSpeed 1.2` 慢慢缩回去。两层的差距就是「刚才掉了多少」。
   回血时残影**立刻跟上**，否则会出现一条比实际血量还长的浅色，看着像没回上。

3. **`HUDController` 加立绘和数字**：`portrait` 从 `CharacterStats.Class.icon` 取，
   变了才写（每帧赋值会触发 UI 重建）；`healthText / manaText` 写 `122 / 140`。

4. **`HudBuilder` 重排**：先把旧的 `HealthBar / ManaBar / SkillBar` 删干净再重建，
   否则新旧两套会叠在一起。菜单还是 **团结 → 修复 HUD 与技能栏**，幂等。

### 18. 三块 UI 各自挂在 Canvas 下，对齐就只能靠手调

**现象**：旧版血条、蓝条、技能栏是三个**平级的 Canvas 子物体**，`Pos Y` 分别是
`-40 / -74 / 40`。想让技能栏「贴着蓝条下面」，就得自己算 `-74 - 18 - 间距`，
改一次高度就要重算一次。

**根因**：它们互相之间没有父子关系，Unity 不知道「蓝条下面」是哪里，
只有一堆写死的数字在假装它们有关。

**解法**：拉一个 `PlayerHud` 容器，四样东西都变成它的子物体，锚点统一 `(0,1)`：

```csharp
// 条和技能栏共用同一个左边距，视觉上天然对齐
private const float BarX = 126f;      // 让开 110 宽的立绘
```

**教训**：UI 的「相对位置」要用**父子关系**表达，不要用两串坐标碰巧对齐。
容器是免费的，多一层就少一堆算术。

### 19. 数字压在会变色的条上，字一定糊

**现象**：白色 `122 / 140` 直接压在红色血条上，血量低时红色变深、字反而更清楚；
血量满时条是亮红，字的笔画就糊成一片。

**解法**：给 `Text` 挂一个 `Outline`（黑、`1.5` 像素），而不是去调字的颜色 ——
条的颜色是变量，字色要能压住**所有**取值，只有描边做得到。

```csharp
var outline = textRect.gameObject.AddComponent<Outline>();
outline.effectColor = new Color(0f, 0f, 0f, 0.85f);
outline.effectDistance = new Vector2(1.5f, -1.5f);
```

**顺带**：数字和条要一起隐藏。`SetBarVisible` 直接开关**整根条的 GameObject**，
文字是它的子物体，所以「死亡后血条消失」不会留下一行孤零零的 `0 / 140`。

### 20. 「太分散」不是间距问题，是缺一块板

**现象**：第一版 HUD 立绘、血条、蓝条、技能格都对上了坐标，但截图一看就是
「四块东西各飘各的」——因为背景是关卡画面，中间没有任何东西把它们连起来。

**解法**：所有部位上面压一层 `PanelBorder`（2px 亮色描边）+ `PanelFill`（深色底），
再把宽度统一（血条蓝条都 440）、技能栏在条下面居中。同一批坐标，加板之后立刻成一块。

**教训**：人眼靠「共同的底」判断一组东西是不是一伙的。分组先想到加底板/卡片，
而不是继续调间距 —— 间距调到 0 它们也还是四个孤立的色块。

**顺带两个贴图坑**：
- 内置 `UISprite.psd` 是**圆角九宫格**，`Image.Type.Simple` 把它拉到 440 宽时，
  圆角会按比例一起拉，出来是一颗「药丸」。要么 `Type = Sliced`，要么换纯白方块。
- 技能格原来一张 `Image` 既当底框又当图标，`SkillBarUI` 每帧把 sprite 换成技能图，
  底框就没了 —— 看着像「图标浮在空中」。底框和图标必须是**两个** `Image`。

## Day 27 · 用素材大师出了一套 UI 图

**目标**：HUD 的底板、格子、技能图标全是纯色块和占位图，用户一句话总结是「太粗制」。

**做法**：用素材大师（图像模块，Ark `doubao-seedream`）生成 6 张：面板、格子、四枚技能图标。
每张都带一张现有的角色帧当参考图，提示词统一写「2px 深黑描边 / 纯色块两阶阴影 / 无渐变 / 16-bit 像素艺术」，
风格才和 Warrior_Idle / Mage_Idle 对得上。

### 21. 生成工具能出图，但「抠底」那一步依赖 ffmpeg

**现象**：`keyImageJob` 直接报 `找不到 ffprobe`，抠像 0 张。

**解法**：不指望外部工具，在 Unity 编辑器里自己抠（`UiArtImporter.cs`）：
读 PNG → 逐像素算「到底色的切比雪夫距离」→ 近的全透明、中间按比例半透明 → 再压掉偏绿/偏洋红的余色（despill）。
图标本来就是「纯色平底 + 深黑描边」，这条最简单的阈值法抠得比专门工具还干净。

**教训**：图像生成和图像后处理是两件独立的事，工具链断了一环不代表整条路走不通。

### 22. 九宫格边框的粗细不是「贴图像素」，是 `spriteBorder / PPU × 100`

**现象**：1024 的图、边框在图上占 175px，直接拖进 UI 是**175 个 UI 像素**——`600 × 174` 的 HUD 板根本吃不下。

**解法**：`TextureImporter.spritePixelsPerUnit` 一起改。`175 / 730 × 100 ≈ 24px` 正好是这块板想要的边宽；
格子 `50 / 640 × 100 ≈ 8px`。**边框粗细是可调的旋钮，不是贴图的属性。**

**顺带**：`Image.Type.Sliced` 只认 `spriteBorder`，`Simple` 会把四角花纹一起拉糊；
内容要往里让开边框那一圈，否则立绘和血条会压在花纹上（这次让了 24px）。

### 23. AI 画得出物件，画不出「可拉伸的渐变」

试过让模型画一条「从上到下三段式的进度条填充」，出来的是浅灰底 + 细横纹（像 CRT 扫描线），
根本没法用。**结论**：条的形状（面板/格子）交给 AI，条的填充颜色继续用纯色 + 2px 高光 ——
可拉伸的东西要的是「每个像素都一样的竖直条纹」，这正是扩散模型不擅长的。

## Day 28 · 战士特效重做 + UI 字号

**目标**：挥砍只有一条细刀光、旋风斩和战吼几乎「无感」，UI 上的数字和 K/L/U/I 角标又偏小。

**做法**：
- 刀光从 3 层横截面改成 5 层（内柔光 / 内芯 / 亮核 / 外刃 / 1.24 倍半径的柔光裙），亮核再往白里偏一点 —— 浅色地面上才看得见。
- 新增 `FxPuff`：一张图 + 一条寿命曲线（缩放/淡出/自转/漂移）的通用一次性特效，打击火花、绕身漩涡都用它。
- 命中火花只在这一下**真的打到人**时放（判定循环里记 `alreadyHit.Count`），空挥不冒火花。
- 旋风斩、战吼的表现图**直接复用技能图标**（Icon_Whirlwind 的空心风刃环 → 漩涡，Icon_Warcry 的同心环 → 冲击波）：同一张图在格子里和场景里天然一致，也省一次生图。

### 24. 特效「没感觉」往往不是图不好，是只亮了一下

**现象**：战吼只有一圈环在放大、旋风斩只有一圈刀光在转，看着像「贴图在缩放」。

**解法**：给每件事补上**层次和时间差** —— 战吼变成内外两圈（内圈快、白热；外圈慢、红色，外圈还慢慢转）、旋风斩多一层绕身漩涡（`spin: 420`）+ 命中火花、刀光多两层柔光裙。
一层不动图、只叠数量和速度差，观感立刻从「一个东西在变大」变成「一股力量在扩散」。

### 25. 一次性的小特效不该各写一个 MonoBehaviour

**现象**：命中火花、漩涡、冲击波各自要「缩放 + 淡出 + 定时删」，三份几乎一样的代码。

**解法**：抽成 `FxPuff.Spawn(sprite, pos, color, life, startScale, endScale, spin, drift, parent, sortingOrder)`，
调用方只写一行。要加新特效（受击烟、拾取光）不需要再写类，只要一张图 + 一个 Spawn。

### 26. 角标 14 号字在 62px 的格子里等于看不见
**现象**：技能格的 K/L/U/I 角标是 14 号，实际游戏窗口里缩到 1.5 倍还是糊成一团。

**解法**：角标 14→20 号、矩形 24×20→30×26；血条数字 18→22、蓝条 15→19；背包属性行 22 号、物品名 17 号。
**字号要按「UI 参考分辨率的像素」想，不是按「屏幕看起来还行」。**

### 27. 网格刀光在起手的两帧里「没有形状」

**现象**：`SwordTrail` 是「每帧记一次剑尖位置、连成带子」，但挥砍只有 0.19 秒 —— 头两帧只有 1~2 个采样点，
带子还没长出来，玩家看到的第一个画面是「什么都没有」，然后突然出现一条弧。

**解法**：起手瞬间额外贴一张画好的月牙弧（`FX_SlashArc`，0.15 秒内胀大并淡出），
网格刀光继续负责「扫过去的余晖」。**瞬时冲击靠贴图，连续拖尾靠网格** —— 两件事分开做，各用各的长处。

弧的朝向：贴图约定「凸边上沿朝 +Y、宽 1 单位」，所以旋转角 = 挥砍中段角 − 90°，凸边正好对着剑扫出去的方向。

### 28. 弹道只有一颗球在飞，看不出「打出去了」

**现象**：法师的法杖弹和火球就是一颗球匀速平移，命中时「啪」一下消失。

**解法**（全在 `Projectile.cs`，火球/法杖弹/箭共用）：
出膛时在枪口崩一小团本体图（0.09 秒）、飞行途中每 35ms 留一张会缩小的残影（拖尾）、
命中时炸一团 `impactSprite`（撞墙小、打人大）。命中染色跟着弹道颜色走 —— 蓝色的球不能炸出橙色的花。

### 39. 抗性写成「减伤百分比」而不是「免疫」

**现象（如果按直觉实现就会这样）**：给玩家加一条「火抗 100%」，火球打上去 0 伤害 ——
Boss 的火球变成摆设，构筑里「堆抗性」直接变成「无敌」。

**解法**：抗性是**减伤比例**，不是开关。

- `StatType` 加四条：`KnockbackResist / PoisonResist / FireResist / IceResist`，值都是 0~1；
- `DamageInfo` 加 `Element`，`AttackData` 加 `element` 字段 —— 伤害从产生那一刻就带着元素；
- **防御先算、抗性后算**（两个都是乘法，顺序其实不影响数值，但写在 `Health` 里同一个方法里，读代码的人一眼能看到「这道伤害被扣了几次」）；
- 抗性上限 **90%**（`Mathf.Clamp(resist, 0f, 0.9f)`）：留 10% 保底，火抗堆满也不是无敌；
- 减免后的数字**写回 `DamageInfo.Amount`** 再抛 `Damaged` 事件 —— 飘字、受击特效、未来的伤害统计拿到的都是实际伤害，不是面板值。

击退抗性单独在 `HitReaction` 里乘：它不减少伤害，只让「被打飞多远」变短，上限同样 90%。

**为什么抗性不做成「元素伤害减免 vs 物理伤害减免」两套**：物理这条通道已经有「防御」了，再加一套会变成两条减伤曲线互相叠，
玩家算不清自己为什么只掉这么点血。**一条通道一个名字**。

### 40. 换房间清了技能、忘了清「动作」

**现象**：放完旋风斩/三段连击，趁动作还没播完走进门；到了下一间房，人站着不动，
但贴图还停在挥砍那一帧 —— 看起来像「进新房间还在攻击」。

**根因**：动作是**表现层的倒计时**，不是数据。`RoomManager.ResetPlayerTransient()`
当时只清了技能（蓄力、旋风斩、战吼、回血法阵）和攻击冷却，没清
`WarriorVisual._clip / _spinTimer` 和 `MageVisual._castTimer / _attackTimer / IsCharging`。
房间切换要淡出淡入几百毫秒，这段时间正好够一个 0.3 秒的挥砍序列播到一半。

**解法**：给 `IPlayerAnim` 加 `CancelAction()`，两套表现层各实现一遍（清计时器 + 回待机第一帧，
但**不清 `_dead`**：死亡姿势该保持住），再由 `PlayerVisualSwitcher.CancelAction()`
统一转给当前启用的那套，最后在 `RoomManager.ResetPlayerTransient()` 里调一次。

**教训**：换房间要清的东西分三类 —— **数值状态**（血/蓝/冷却，要留着）、
**技能效果**（法阵/漩涡/战吼，要结束或结算）、**表现层计时器**（动作序列/受击/蓄力，要掐断）。
前两类容易想到，第三类属于「看不见的状态」，只有看到「人站着还在挥刀」才会想起来。

### 41. 长按 J 打不出第二刀

**现象**：点一下 J 出一刀，**按住**不放却不会继续 —— 想打三段连击必须连点三下。

**根因**：攻击输入用的是「按下」latch —— `InputAction.performed` 只在按下那一帧触发一次，
长按期间不会再产生事件，所以 `ConsumeAttackPressed()` 永远是 false。
连击段数本身没问题（窗口 0.45 秒内会推进到第二段），是**根本没有第二次攻击请求**。

**解法**：`PlayerInputReader` 加一个实时属性

```csharp
public bool AttackHeld => _actions.Player.Attack.IsPressed();
```

`PlayerAttacker.Update` 改成「按下 **或** 按着」：

```csharp
bool attackPressed = _input.ConsumeAttackPressed();
bool attackHeld = _input.AttackHeld;
if ((attackPressed || attackHeld) && _cooldownTimer <= 0f) { ... }
```

**注意**：latch 还是照样消费掉，否则「按下的那一下」会一直留着，导致下一帧又多打一刀。
两者并存才是对的 —— **按下立刻响应，按着按冷却节奏续招**。

### 42. 大厅装饰的交互别写死在房间里

**需求**：大厅多摆些中世纪陈设，走到特定的装饰前能按 E 交互（比如技能树），内容先不做。

**做法**：装饰自己带 `LobbyInteractable`，房间只负责「找最近的那个」。

```csharp
LobbyInteractable near = FindNearbyInteractable(playerPosition);
if (near != null) { RefreshHint($"按 E {near.Prompt}"); if (IsStartPressed()) ShowInteractPanel(near); return; }
```

- 交互半径、提示语、弹出内容都挂在装饰上（public 字段，跟 `LobbyPedestal` 一个路数，由生成器直接赋值）；
- 大厅每帧只遍历一次「场景里所有 `LobbyInteractable`」的缓存数组，加装饰不用改大厅代码；
- 站在装饰前时 **交互优先于进门**（`return` 掉后面的门判定），避免两个 E 抢键；
- 面板 2.6 秒自己收，不需要点按钮 —— 它只是「交互成功」的反馈，不是对话框。

**教训**：凡是「玩家走到某处会发生什么」，都让**那个物体**自己说，而不是让房间维护一张坐标表：
坐标表会随美术调整失配，而物体自己不会。

### 29. 一把「共用」的命中特效，让两个职业打起来一模一样

**现象**：战士的命中火花做完之后，法师打怪也是同一朵白热星芒 —— 刀砍和法球看起来是同一个东西。

**根因**：`PlayerAttacker`（近战）和 `Projectile`（弹道）是两条完全独立的代码路径，
但特效图只有一张，两个职业共用，视觉上就抹平了差异。

**解法**：按「打出来的东西」分配特效，不是按「谁打的」：

| 来源 | 命中图 |
|---|---|
| 战士近战 | `FX_HitSpark` —— 白热四角星芒 + 放射火花（刀刃劈开的形状） |
| 法师普攻 | `FX_ArcaneBurst` —— 白核 + 细青环 + 紫色符文碎片（法术碎裂的形状） |
| 火球 | `FX_FireBurst` —— 白核 + 火舌 + 暗红火烟（烧炸的形状） |

三张都是「中心白热 + 向外炸」，但**外圈形状完全不同**：星芒、碎片、火舌。
玩家不需要看颜色就知道这一下是什么打出来的。

### 30. 法球「一卡一卡」还能被法师追上

**现象**：法师普攻的奥术球飞起来一顿一顿的，冲刺一下甚至能跑到球前面。

**三个独立的毛病叠在一起**：

1. **弹速低于冲刺**。球是 14 单位/秒，冲刺是 18 —— 玩家按住冲刺当然追得上。
   弹道必须比玩家最快的移动方式快，否则「远程」在体感上就不成立（改到 22）。
2. **在根节点上自转**。刚体开了插值后，transform 每帧都被物理插值结果覆盖；
   我每帧再手动转一次，等于和引擎抢同一个 transform，画面就是一顿一顿的。
   解法：给贴图垫一个空子物体当转轴，转子物体（`EnsureSpinPivot`）。
3. **拖尾按时间留**。快的地方断成虚线、慢的地方挤成一团疙瘩 —— 改成按**距离**留（每 0.55 单位一张）。

一个表现问题，往往是三处各错一点叠出来的。看现象先怀疑「唯一的原因」是纯直觉；实测数据（速度 14 / 冲刺 18）反而最快。

> Day 5 的两个坑记在 `07-Day5技能系统配置.md`：§6.1 `Rigidbody2D` 的 `Simulated` 被取消勾选（表现为投射物既不动也不碰撞），§6.2 默认值看起来总是「对的」（`AttackData.hitboxOffset` 默认 0.8，新建资产时会以为它本来就对）。

### 31. 换房间时，玩家带着上一间的状态进了门

**现象**：在门口举着蓄力火球进门，下一间第一帧松手就是一发满蓄力；回血法阵跟着人走进新房间继续跳绿字；旋风斩的漩涡挂在身上跟到下一间。

**根因**：这些状态一份都不属于「房间」，而属于「玩家」——

| 状态 | 存在形式 | 为什么房间销毁带不走 |
|---|---|---|
| 蓄力 | `SkillCaster._chargeSlot/_chargeTimer` | 是玩家组件里的字段 |
| 旋风斩 / 战吼 | 玩家身上的组件 + 它挂的子物体 | 只 `Destroy(this)`，子物体留在玩家身上 |
| 回血法阵 | 独立物体 `__HealCircle` | 圆心每帧跟 `_caster.position` 走 |

换房间的流程是「销毁旧房间 → 实例化新房间 → 把人挪过去」，**玩家自己从头到尾没被动过**，所以挂在玩家身上的东西当然一件不少。

**解法**：在 `RoomManager.BuildRoom` 里、挪人之前插一句 `ResetPlayerTransient()`，按上面那张表逐项清：

- `SkillCaster.ResetRoomState()`：`CancelCharge()` + 停掉持续技能 + 结算法阵
- `PlayerAttacker.CancelPendingAttack()`：连击段数和冷却归零（否则进门第一刀直接是第二段）

两个刻意的选择：

1. **法阵是「结算」不是「掐断」**：蓝和冷却已经付过，把没跳完的几次一次性补上（`FinishNow(settle: true)`），玩家不会觉得换房间白亏一个技能。
2. **血量/蓝/冷却不动**：这些是这一局要带着走的，重置了肉鸽就没有连续性。

一条通用经验：**「加状态」和「清状态」要成对写**。加的时候顺手想一句「这个状态什么时候该消失」，比出问题再翻代码便宜得多。

### 32. 刀光比换房间活得久

**现象**：换房间后的第一秒，人还没站稳，身上又亮了一下刀光。

**根因**：`SwordTrail` 生成的网格是 `new GameObject("__SwordTrail")` 再 `SetParent(owner)` —— **挂在玩家身上**。
它的寿命（Slash 0.19 秒）和「淡出 → 销毁 → 实例化 → 淡入」这套换房流程是同一个量级，所以上一间最后一下的刀光，
正好能活到下一间开场。它不属于房间，所以销毁房间时不会被带走。

**解法**：`RoomManager.ClearTransientFx()`，把「已经生成出来、但只是表现」的东西全清掉：

```csharp
foreach (var trail in _player.GetComponentsInChildren<SwordTrail>(true))
    Destroy(trail.gameObject);

foreach (var puff in FindObjectsOfType<FxPuff>())
    Destroy(puff.gameObject);
```

判断标准很简单：**它有没有数据含义？** 血量有，刀光没有 —— 没有的那一类，换场景时一律可以扔。

### 33. 左键既想穿又想起卖，就只能先问一句

**现象**：背包里左键点物品，原来直接穿上；想卖却没有入口。而且「一件东西能做的事」本来就不止一件（装备/服用/出售）。

**解法**：不动 `ItemSlotWidget`（它只转发点击），在 `InventoryUI` 里加一张小菜单 `ShowItemMenu(widget)`：
- 用 `RectTransformUtility.WorldToScreenPoint` 把被点的格子换成屏幕坐标，再 `ScreenPointToLocalPointInRectangle` 换算到窗口坐标；
- 菜单默认开在格子右下 16px，贴边时翻到左侧/上方；
- 两个动作按钮 + 取消，按钮是 `SmallButton`（只转发 `owner.HandleMenuClick`，文案和能做啥都由 `InventoryUI` 决定）。

顺带把金币补上：`Inventory.Gold / AddGold / TrySpendGold` + `GoldChanged` 事件 —— 卖东西总得有个数字落地，不然「出售」看不出意义。

### 34. 深色底上的细笔画中文，不加描边就是一坨灰

**现象**：背包换皮后文字「看不清」，尤其属性卡那些 20 号的小字。

**根因**：`Text` 默认没有描边，深蓝底 + 米白字在 1x 缩放下笔画边缘直接糊进背景；另一个坑是字体兜底顺序里 `SimSun`（宋体）排前面的话，小字号横笔只有 1px，等于没有。

**解法**：`NewText()` 统一 `AddComponent<Outline>()`（`effectColor (0,0,0,0.85)`、`effectDistance (1.2,-1.2)`、`useGraphicAlpha`）；字体顺序改成雅黑 UI → 雅黑 → 等线 → 黑体 → 苹方 → 宋体；小字号整体加 1~3 号。

### 35. 描边不是越粗越清楚

**现象**：加了描边以后还是「太模糊」，字看着发胖、边缘发毛。

**根因**：两件事叠在一起 ——

1. 描边 1.2px + 0.85 黑色，在 20 号字上等于给每个笔画外扩了一圈，相邻笔画黏在一起；
2. `CanvasScaler.matchWidthOrHeight = 0.5`：窗口宽高比一偏离 16:9，缩放比就落在 0.72、0.76 这种小数上，动态字体的点阵被重采样一次，笔画更虚。

**解法**：描边收到 1px / 0.7 alpha；`matchWidthOrHeight = 1`（按高度对齐，1080 高时正好 1:1）。真要更清楚只能换 SDF 字体（TextMeshPro），Legacy `Text` 到这就到顶了。

### 36. 网格刀光转满一圈，首尾相接

**现象**：旋风斩时人身上套着一圈白环，环上有一段特别亮、正好落在下方，像一道剑气朝下压着人。

**根因**：`SwordTrail` 每帧采一个点，转满 360° 后首尾重合，环上最新的那段 `fade` 最大、最亮。

**解法**：整圈技能（Spin）不画网格刀光，改用它自己的 `auraSprite` 贴图；普通挥砍照旧用网格。

### 37. 刀光成「一节粗环」

**现象**：按 J 普攻，角色前面出现一节又厚又匀的白色弧形。

**根因**：三个原因叠在一起 ——

1. 横截面 5 层的 alpha 是「中间最亮、两侧各 0.55」，等于一块均匀的板；
2. 外圈还有 1.24 倍的柔光裙；
3. `_life = duration × 0.85`，挥砍结束时三个采样点全活着，110° 被摊成整片扇面。

**解法**：亮线挪到剑锋那一侧（`BandT` 第 4 层 = 外缘 1.00 最亮、0.95 alpha），往里迅速衰减（0.55 → 0.08）；外圈柔光砍到 1.12 倍且 alpha 0；`_life` 收到 `duration × 0.55`，只留「刚扫过去」的一小段。

### 38. 干脆用贴图代替刀光

**现象**：网格刀光无论怎么调，都像是在「算」一条带子 —— 挥得快就摊成板、挥得慢就细成线，同一个动作的手感每次都不一样。

**思路**：把一张画好的「扇环」贴在玩家身上，让它绕自己的圆心**转过去**。转过的角度 = 挥砍的角度，转的过程就是挥砍的过程。

**关键约定**（`SlashArcFx`）：

- 贴图里弧的圆心必须在画布正中 —— 否则转起来会「甩」出一个偏心圆；
- 弧半径占画布宽度的比例写死一个常量（当前 0.435），换图只改这一个数；
- 贴图左右对称，所以面朝左时只镜像角度（`180 - angle`），不用翻图；
- 时间轴：前 70% 扫过去（缓出），后 30% 原地淡掉。比挥砍时长长 25%，收尾才不突兀。

**代价**：弧的形状固定，不能像网格那样「从动作里长出来」；挥砍中途转身时贴图不会重新构图。换来的是每次挥砍长得一模一样、且一定好看。
